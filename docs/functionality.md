# Functionality (what the user sees and can do)

The product loop: **capture → see → think → shape → keep**.
Screens are numbered; the number key opens the screen from anywhere when no text field has focus
(`Screen` enum order, user-reorderable in Settings → Tabs). Shortcuts are **Ctrl** chords (⌘ chords were tried and dropped: terminals and
macOS claim them).

| Key | Screen | Role |
|---|---|---|
| 1 | **Brain** (`Home`) | dashboard: vault stats, what needs attention, recent notes, top tags |
| 2 | **Chat** | hub for talking to the model; attachments, vault answers, tools, questions |
| 3 | **Library** | browse every note, rename, chat about a note |
| 4 | **Inbox** | AI-assisted filing of unprocessed notes |
| 5 | **AI notes** (`Compose`) | write or transform notes with AI, refine, apply |
| 6 | **Session** | what happened this run; save a summary note or log; new session |
| 7 | **Usage** | dashboard of tokens, speed, estimated price, habits |
| 8 | **Settings** | tabbed settings (each tab's list scrolls with the cursor in a short window) |
| 9 | **Guide** | in-app tutorial pages (13, incl. Skills) |
| 0 | **Changelog** | what has been built, by theme |

Global keys: `Ctrl+P` command palette · `Ctrl+N` quick capture · `?` key map for the screen · `Ctrl+B` fold the sidebar ·
`Ctrl+C` ×2 quit · `0`-`9` screens (when not typing). Navigation can be a left sidebar, right sidebar or top bar (Settings → Appearance →
Navigation). The sidebar shows badges (inbox count, unsaved session, `…` on Chat for a running reply, `!` when the model waits for an
answer) and folds to icons under 90 columns.

## Brain (Home)

Two columns when ≥100 wide. Left: *Capture* hint, *Needs attention* (inbox waiting, notes with no links, no tags, broken
links), *Top tags*. Right: *Jump back in* (Ask your brain, AI notes, this session), *Recent notes*. Data comes from
`BrainState.index` / `VaultIndex.health(inbox, staleDays)`. Enter opens the highlighted item (Library filter, Chat, a note).

## Chat (hub)

- Chat **opens in browse mode** (field not focused: `j`/`k` scroll, `s` select & copy, digits switch screens); `Enter` starts typing and from then on the
  field has the keyboard (letters never trigger shortcuts). `Esc` goes back to browse mode (then `s` selects: an entry is one of your messages, one Markdown block of a reply, **one tool call, or one tool result**, so each can be ticked and copied alone; a reply header only belongs to an entry of its own message); `?` on an empty message field opens the key map (with text in the field it types a question mark); while a reply (or an Oracul run on its own) runs, `Esc` opens *Cancel this reply?* (`ChatMode.ConfirmCancel`): `Enter` or `y` cancels, any other key keeps going, and the reply keeps streaming while the question is open, so a stray `Esc` never loses a reply. Settings → Console → *Confirm before cancelling* (`confirmCancel`, default on) off: `Esc` cancels at once.
  **Queued messages:** while a reply runs, typing and `Enter` puts a plain-text message in a queue (`ChatSession.queued`, listed above the field as `⏳ queued …`, three at most then a count) instead of ignoring it. A tool turn takes the whole queue at the end of its next tool round (`runTools`): the text joins the turn as your message, so a correction or a clarification reaches the model before its next step. A turn without tool rounds sends ALL the queued messages after its reply as one message, joined with a blank line (`finishReply` → `takeQueued`, the same as a tool round does): a later message is often a correction of an earlier one, so answering them one by one would answer the first without it. If the reply is cancelled or fails, the queue goes back into the field (`takeQueued`). **Backspace on an empty field removes the newest queued message** (after the attachments, like them: `ChatSession.dismissQueued`; the queued line carries the hint); nothing is sent for it. Commands (`/…`) and attachments cannot be queued (a toast says so); `/new` clears the queue.
  (`browsing` starts `true` and is local to the screen, so it resets whenever the tab is opened; `/new` puts the cursor in the field.)
- **Multi-line field**: grows to a quarter of the screen (3–8 rows) with a scrollbar (`WrappedText`); `Alt+Enter`, or `\` then Enter,
  starts a new line; Up/Down move between lines. `Enter` sends. Long pastes are repaired from the clipboard (`KeyDispatcher`).
- **The "/" menu**: a message that starts with `/` (no space yet) opens `slashMatches(SlashCommands + tool specs, typed)` above the
  field (≤8 rows, counted in `below`): ↑↓ choose, **Tab completes** the highlighted name into the field (`/revise `, a trailing space, the caret after it, ready for the text; tools and skills too) and **Enter runs it** (a command runs, a skill is attached as a chip, a tool writes `Use the <tool> tool to `), Esc clears. A command runs through `runCommand` (`/new /history /save
  /note /image /vault /tools /mode /autorun /effort /compact /memory /skills /thinking /flow /goal /artifacts /append /replace /clear`); settings show an ON/OFF/mode badge (`slashState`); a tool inserts
  "Use the <tool> tool to " (tools are called by the model, not typed); the list is grouped commands, skills, tools (`slashMatches` sorts by `SlashCategory`) with a COMMAND / SKILL / TOOL badge per row, and the skills are scanned from the skills folder every time the menu opens (`Skills.discover`, never hardcoded); each entry is coloured by what it is (`SlashKind`: commands cyan, skills purple, read-only tools green, changing tools orange, shell/delete red, web blue) with a glyph and a badge word; each **skill** found in the vault is listed as `/<name>` and attaches
  it as a `◆ skill <name>` chip whose text is added to the message on send (see [tools-and-agent.md](tools-and-agent.md), "Skills").
  **Usage line:** the highlighted entry gets a second row with an example of how to type it with its text (`SlashItem.usage`): `e.g. /revise focus on the edge case`, `/oracul qwen3:30b`, `/compare qwen3:30b`, for a skill `e.g. /<name> <what you want>`, for a tool `e.g. /read_note Trip Planner` from a curated list (`ToolExamples`) or else `usage: /name <required args>` read from its schema (`toolUsage`), `needs no text: just /name` when there is none; commands that take no text show none. The row counts into the menu's height. Typing the entry out with text after it works (`splitSlash`, `send`).
- `@` attaches a vault **note**; `Ctrl+O` attaches **files** (pictures ≤5/10 MB for a vision model, **PDFs** ≤20 MB, text files ≤5/2 MB).
  Backspace on an empty field removes the last attachment.
- `/vault` toggles **answer from vault** (each question searches the vault; the reply lists `Sources` and cites `[[Note]]`).
  `/tools` toggles tools, `/thinking` toggles the live thinking pane, `/effort` (old name `/think`) picks the reasoning effort from the levels the model lists (`/effort xhigh` sets it directly) (model default, off, on; what Ollama lists for it), `/mode` cycles ask → auto → plan, `/autorun` toggles running shell commands without asking, `/oracul`, `/compare`, `/revise` and `/takeover` use the Oracul model (below), `/compact` summarizes the older part of the chat (below), `/memory` opens `ARCANA.md`, `/skills` toggles skills and lists them.
- Replies stream; the footer shows `✓ Done · time · ↑ prompt ↓ output tokens · tok/s` (a round that ended in a tool call shows a quiet
  `· step` line). The "thinking" status names the model. A reply keeps running when you leave the screen: with an empty field the
  number keys (and `Ctrl+P`) switch screens.
- **Status bar under the field** (`StatusBar(chatStatus(…))`; it **wraps onto more rows in a narrow window and never hides a fact**; `Σ 74k all models` is the session's tokens over every model and feature, the `↑ ↓` arrows are this chat's main model only, and `est.` is worked out from the Σ figure): model pill, memory size (`✎ memory 2.3k`), context gauge (`ctx █░░ 3%
  3.9k/131k`: last prompt + reply against `contextTokens`, else the window Ollama really loaded (`/api/ps`), else the model's `context_length`; never more than the model supports; written `256k`, not `262k`; a window under 32k shows `⚠ ctx 4k`), tokens in
  and out (`↓` and the bottom bar's `⚡ N tok` also count the reply tokens streaming right now via `AppContext.liveTokens`, replaced by Ollama's exact figures when the request ends; `↑` prompt tokens are exact and step once per model round), estimated price (`est.`, from Settings → Ollama → Price per million tokens), session time, tool-mode pill. Least important
  items drop first on a narrow terminal.
- Chats are **kept automatically** (`ChatStore`, one JSON per chat; the latest reopens at start; `/history`). Leaving never asks (only
  with *Keep chats* off does Arcana ask). The header says `kept in history · not in vault (Ctrl+S)`; **Ctrl+S "Save to vault"** (in its dialog **Ctrl+O** picks an existing note to overwrite with the whole chat or the last answer: `overwriting` → the `PickTarget` picker → `ConfirmReplace` → `Vault.replace`, which backs the old text up) turns
  the chat (or the last answer) into a note. `/append` and `/replace` use the last answer.
- Output is rendered Markdown (see [ui-internals.md](ui-internals.md)): boxed tables, closed code boxes with line numbers and
  highlighting, coloured figures. Select mode: ↑↓ move, Space ticks, `c` copies (Markdown or plain per Settings), `b` code/tables only.
- Dialogs inside Chat (buttons **inside** the dialog): approvals, folder grants, questions from the model; see
  [tools-and-agent.md](tools-and-agent.md).

### Tools in Chat (opt-in)

With *Settings → Tools → Tools in Chat* on (or when a dialog offers it), the model may call the tools listed in
[tools-and-agent.md](tools-and-agent.md): read-only ones run at once; changes, deletes, moves, commands and web fetches always ask.
Modes: ask / auto / plan. Shell commands and web pages are separate switches, off by default.

## Memory file (ARCANA.md)

The memory file (the Chat status bar's `✎ memory 3k` pill turns orange, `⚠ memory 8k of 11k: end cut`, when the file is longer than `Vault.MEMORY_LIMIT`; the real length is `Vault.memoryLength()`) (by default the vault note `ARCANA.md`; **Settings → Prompts → Memory file path** can point it into another vault folder or anywhere on the computer, e.g. `~/Documents/arcana-memory.md`: `Vault.memoryFile()`, which `memory`, `ensureMemory` and `remember` all use; a missing folder is created) (first 8,000 characters, no frontmatter) is added to every chat's system prompt (`Vault.memory()` →
`Prompts.chatMessages(memory = …)`; Settings → Prompts → *Memory file*; the status bar shows `✎ memory`). `ChatSession.offerMemory()` runs
when Chat opens: if the vault has no `ARCANA.md` and `memoryOffered` is false it creates one from `Vault.MEMORY_TEMPLATE` (fifteen rules
for using tools, plus empty sections) and shows "Memory file created" with an offer to open it; the flag then stays true, so a file the user
deletes comes back only through `/memory`. The `remember` tool appends to its "Remembered" section (always asks). It **does not add a fact twice** (`MemoryLines.similar`: equal after lower-casing and dropping punctuation, or at least 80 % of the words shared; it answers "Already remembered: …") and **refuses a line that names a note that is not there** (a `[[link]]` or a `.md` path: `Vault.noteExists`; the message tells the model to get the exact path with `find_files`). `/memory check` lists repeated lines and dead note paths (`Vault.auditMemory`) in a panel; `y` removes the repeats (`Vault.cleanMemory`: the first of each stays), dead paths are only listed, for you to fix in the file. Only this vault's memory file is touched, never your own `~/.config/arcana/ARCANA.md`. `ToolBox.cheatSheet()`
adds the real tool list to the same prompt.

## Skills

A skill is a runbook in the vault (`.arcana/skills/<name>/<name>.skill.md` (hidden folder; the older `Skills/` still works, `arcana --migrate` moves it), or in `~/.config/arcana/skills/` for every vault, plus `reference/` and `scripts/`; its results go to a folder it names with `output:`).
Full explanation: [skills.md](skills.md). What the user sees and does:
- **Find:** type `/` in Chat: skills are listed after the commands, before the tools (badge `SKILL`, name `◆ /name`, hint = the first sentence of `description:`); the folder is rescanned every time the menu opens. `/skills` toggles skills (Settings → Tools → *Skills*, *Skills folder*) and shows what was found and what needs attention.
- **Use:** picking one attaches the chip `◆ skill name` (Backspace on an empty field removes it); type the task and send. Arcana adds the skill's text to the message, so the model need not call `use_skill`; that question may take up to 40 tool rounds. With tools off a toast says the skill cannot act.
- **Progress:** if the skill lists `requires:`, the Chat status bar shows `◆ name 7/11` (purple running, green ✓ done, red ✕N skipped). If the model tries to finish with a step missing, Arcana sends it back (hidden message); after 3 ignored tries on one step it gives up on that step. Skills without `requires:` get no badge and no gate. The badge goes at your next message or `/new`.
- Every change, command and fetch a skill leads to still asks for approval as usual.

## Library

Views (←/→): All, Recent, Inbox, No links, No tags, Broken links, Stale, Tags. From the sidebar the Library opens on the view of **Settings → Library → Opens on** (`libraryTab`, default All; a link from the Brain screen still opens its own view once: `Navigator.libraryFilter` is read and cleared, it used to stay and make the Library open on the last linked view, for example Tags). **Settings → Library** also sets *List width* (`libraryListPercent`, 20-60 %, default 30), *Sort by* (`librarySort`: newest first or title A-Z, for the lists ordered by date), *Preview pane* (`libraryPreview`) and *Tab counts* (`libraryCounts`). The list is a **tree of folders** by default (`AppConfig.libraryTree`, `t` toggles, Settings → Library → *Library as a tree*): `libraryRows(notes, expanded)` (`screens/LibraryTree.kt`) puts subfolders first (A to Z, case-insensitive) then the notes in the view's own order; a folder row shows `▸`/`▾` and how many notes are below it; only folders in `AppContext.libraryExpanded` list their children (the set survives leaving the screen, not a restart). `Enter`/`Space` fold or unfold (`Enter` on a note reads it), `l` unfolds or steps in, `h` folds or jumps to the parent folder, `+`/`-` unfold/fold all. While a filter is typed the matches are listed flat with their paths (`Esc` brings the tree back); the tag list is not a tree. The Brain screen's "open this note" unfolds the note's ancestors (`ancestorsOf`) and selects it; a highlighted folder shows its path, note and subfolder counts in the preview pane. Left list + right preview (frontmatter, links, backlinks,
related notes). Keys: `Enter` read, `a` AI on this note (opens AI notes with the note preset), `c` **chat about it** (a new chat with the
note attached; a saved chat note carries its whole transcript), `e` **edit** (`LibraryMode.Edit`: the whole file in a multi-line `TextFieldState`, Enter = new line, Ctrl+S = `Vault.write`, Esc leaves and asks `ConfirmDiscard` when changed; saving is refused when the file differs from what was opened; logged as `replaced`), `r` **rename** (a field with the current name; the note stays in its
folder and the `[[links]]`/`![[embeds]]` to it in other notes are rewritten like Obsidian does, outside code; `Vault.rename`), `o` open in
Obsidian, `d` trash (moves to `.trash`, asks first), `/` filter, `p` process the inbox (Inbox view); the Tags view browses notes per tag.

## Inbox

Lists notes in `inboxFolder`. "Process with AI" asks the model for a JSON plan per note (`InboxProcessing`): title, tags, a one-line
summary, links to existing notes, destination folder. `Enter` reviews a note, `p` processes all; in the review `Tab` moves between editable
fields, `Enter` applies, `Ctrl+X` skips. The plan is validated against the vault (links must exist, folder must exist or be a sensible new
one), previewed, then applied with `Vault.processInboxNote`, which first backs the original up to `.trash`, merges tags into frontmatter,
adds a summary callout and a `## Related` section, then renames/moves.

## AI notes (Compose)

Tasks: Write a new note · Turn pictures into a note · Summarize · Improve · Continue · Translate · Action items · Connect (suggests tags
and links from what the vault already contains) · Custom. Input accepts attachments (pictures, PDFs, files). The result is a **draft**:
refine (`f`), add more (`m`), undo (`u`), redo (`r`), then save as new (`n`), add to a note (`a`), replace the source note (`w`, with
backup), or copy. Leaving with an unapplied draft asks first (the only leave guard besides *Keep chats* off).

## Session

Every run is a session logged to `~/.config/arcana/sessions/` as it happens (asked, task, created, appended, replaced, renamed, deleted,
saved, captured, processed, attached, tool). Actions: save a **summary note** (model-written from the log and chat transcripts) or the
**plain log** into the vault; **start a new session** without restarting. Quitting never asks about unsaved activity.

## Capture (`Ctrl+N`)

One line becomes `- HH:mm text` at the end of today's daily note. **`Tab` / `Shift+Tab` in the dialog choose where** (`AppConfig.captureFolder`, remembered; blank = daily note, else one of `Vault.rootFolders()`: the folders at the top of the vault, no hidden ones and no `attachments`): in a folder the thought is a new note of its own (`Vault.captureNote`: named after its first line, cut at 60 characters, a number when the name is taken, only a `created` property; attachments are embedded under the text). A remembered folder that no longer exists falls back to the daily note (`captureFolderNow`). The daily note path/format comes from Obsidian's
`.obsidian/daily-notes.json` when present, else Settings (`dailyFolder`, `dailyFormat`). `Ctrl+O` attaches any file(s): copied into
`<outputFolder>/attachments/` and embedded as `![[name]]`.

## Oracul (second opinion)

`core/Oracul.kt`, `ChatSession.secondOpinion / compare / maybeConsult`. Settings → **Helpers** (and **Opinions**, **Flow**, **Skills**, the old Oracul tab split in four): *Oracul model* and *Judge model* (the same model picker as Settings → Ollama → Model, with a "None" entry; `Editor.Model` carries the setting it edits), *Automatic second opinion* (`oraculAuto`: `off`, `problems` (default), `always`).

- **Which model runs what:** the worker is `AppConfig.model` (unchanged). The Oracul model reviews (`/oracul`) or answers the same question (`/compare`); the judge model (else the Oracul model) compares the two answers. Each call gets its own `OllamaClient { config.copy(model = …) }`; nothing is sent to a model that is not set; a blank Oracul model means the whole feature is off and `/oracul` says "Choose an Oracul model first". Ollama loads one model at a time on a small machine, so the first call after a worker reply takes a moment.
- **Automatic:** after every finished reply `maybeConsult` asks `Oracul.due(config, turnFacts)`: `problems` = two or more failed tool calls in the turn (`Error:`, timeouts, non-zero exit) or a skill run that had to skip a required step; `always` = every reply. `problems` also fires when the last **`stuckTurns` turns in a row** (default 3) each had a failed call (`Oracul.failedStreak`, `stuckTurns`: the user keeps coming back, the worker keeps failing). A failure of the Oracul is ignored. `/oracul` always works as the manual override.
- **Stuck in a turn (`stuckAdvice`):** while the worker is in its tool loop, every **`stuckCalls`-th failed tool call of the turn** (default 4) (`stuckCalls`, default 4, `Oracul.stuckLevel`; `0` = never; not for `off`) makes `runTools` ask the Oracul before the next round: it reads the task and the attempts so far (`Oracul.attempts`: each call with its arguments and its result, failures marked, shortened, newest last; `stuckRequest`) and says what is really going wrong, which attempts repeat the same mistake and what to do differently. Its answer is added as an ordinary review block (`Oracul.stuckMessage`, `Ψ Second opinion · <model>`) at the end of the round, so the worker's next request already contains it; the Oracul has its tools as usual (reads free, changes ask). Once per 4 failures (4, 8, …), nothing when it cannot answer or is busy, never breaks the worker's turn, Esc cancels it with the turn. A turn that got such advice gets no further automatic review after its finished reply. `consulting` shows `Ψ <model>…` meanwhile.
- **Who is working, in the bars:** the Chat status bar has one block for the main model and the Oracul, the model that works now first as the filled pill (the main model's accent, the Oracul's and judge's orange with `…`) and the other quietly after it (`waiting` for the main model). The bottom bar swaps its badges the same way and collapses the Oracul's to its glyphs (`Ψ ⚖`) in Chat. The reply line says `Ψ <model> is answering…`, `⚖ <judge> is judging the answers…` or, at the start of a tool round, `<model> is reading the conversation again…`. **Esc** stops an Oracul or judge run that works on its own (nothing is added); a new message cancels a stale automatic one. Over columns the comparison's title colours the model names like their pills.
- **Judge automatically (`oraculJudgeAuto`, Settings → Opinions, off by default):** when an automatic second opinion is due, `maybeConsult` runs `compare()` instead of `secondOpinion()`: the Oracul answers too and the judge compares, so the judge works without `/compare`. Three model runs instead of one. Stuck advice mid-turn and skill reviewers stay single opinions.
- **Tools (`oraculTools`, Settings → Helpers → *Oracul may use tools*, on by default):** when Tools in Chat is on and the Oracul model has the `tools` capability (`/api/show`), it gets the worker's toolbox (`oraculToolbox`: the same allowed folders, project, shell/web switches and Plan mode as the worker) and a short tool loop (`oraculAgent`, at most `toolSteps` rounds, capped at 10; the last round offers no tools). It is told to CHECK with them, not to change anything on its own initiative. **Reads follow *Read without asking*; changes, commands and web access ALWAYS ask, even in Auto mode and with auto-run on**, in a dialog headed `Ψ Oracul · …` with the model named; no "always" choice. It has no `ask_user`, `request_mode` or `request_access`, so it cannot ask for more power, and a path outside the allowed folders is just an error (no folder dialog). Denied calls are reported back to it. What it used is appended to its block (`_Checked with: read_note, grep_files ×2_`), its calls are recorded in Usage → Tools, and `/compare` lets it use tools for its own answer too. Without tools (off, no capability, setting off) it only reads the question and the answer.
- **`/revise`:** asks the worker to revise its last answer with the open opinion (`Oracul.hasOpenOpinion`: no answer or user message after the block yet); the request is sent as your message (`Oracul.REVISE_PROMPT`), the opinion is already in the history. The palette entry is enabled only while an opinion is open.
- **Split view (`comparisonView`, Settings → Console → *Comparison view*, `side` by default, or `stacked`):** a `/compare` block is drawn as columns (`Chat.sideBySide`): over each answer a filled name pill (the main model's in the accent colour with its family glyph and `· main`, the Oracul models' in blue / purple / green with `Ψ` and `· oracul`), a thin rule in the same colour, the answers next to each other with a dim `│` between them, the judge's verdict under them across the whole width behind an orange `⚖ Verdict · <judge>` pill. At most three columns, each at least 38 cells (`columnCount`); more answers than columns continue in further rows; a window that cannot hold two columns stacks the answers as before (so does a block of another shape). The split is read by `Oracul.comparisonParts` from the names in the block's title, not from `## ` lines, so an answer with its own headings stays whole. Only the drawing changes: the stored message, select and copy, `/save` and what the main model sees are the same.
- **More than two (`oraculExtra`, Settings → Helpers → *More Oracul models*, comma-separated):** `/compare` asks the Oracul model and every extra model in turn (`Oracul.models`: no blanks or repeats; each loaded in turn, so more models mean a longer wait), then the judge sees ALL answers (`ANSWER 1` is the worker's) and picks the best or merges them. An extra model that cannot answer (not installed, empty reply) is left out and named in a closing `Left out:` line of the verdict; the first Oracul model must answer or nothing is added. The block heading is `Comparison · worker vs a, b, judged by judge`.
- **Memory advice for the chosen models:** a model already chosen (main, Oracul, judge, a skill's planner / worker / reviewer) that does not suit this machine's memory is said so, with a better installed model: under the selected Settings row, in the notice after saving it (red when it would swap to disk or run on the CPU) and as an orange `⚠` in the Chat status bar for the Oracul (`ModelFit.advice`, `AppContext.memoryAdvice`).
- **Memory fit and suggestion (`core/ModelFit.kt`):** the model pickers of Settings → Helpers (and the other model settings) say per model whether it fits this machine: `fits with the main model` (both stay loaded), `fits alone (swaps with the main model)` (Ollama swaps them, several seconds each time), `too big for this memory` (red: it would swap to disk or run on the CPU), from the size on disk ×1.2 against 70% of the physical memory (`ModelFit.fit`; a rule of thumb, not a measurement). The picker header names the memory. `★ suggested` marks the Oracul pick (the largest model that fits at all, with tools when *Oracul may use tools* is on, never the main model or an embedding model) and the judge pick (the largest that stays loaded with the main model). With *Oracul server* set the memory of that machine is unknown: no verdicts. Nothing is chosen for you.
- **Repeated calls are answered, not run:** inside one turn an identical read, search or web fetch (nothing changed in between) returns a short "you already made this call, the result is above" instead of running again or asking you again for the same address (`ChatSession.turnCalls`). A new message, any change or command, or a `wait` starts over; entries also expire after 45 seconds (Settings → Tools → *Remember repeated reads*, 0 = off), and a failed result is never remembered. `wait`, `current_time` and `elapsed_time` always run. Nothing is cached across turns: a file may have changed.
- **Loop guard (`LoopGuard`):** two checks against a model that goes round in circles without an error, both without another model. **Text:** while a round streams, about every 160 characters `Generation` looks at the last 12,000 characters of the thoughts and of the answer: when the last 80 characters already stand `loopRepeats` times in them (default 5; not in an open code fence, never for a line of dashes or a table rule) the stream is closed. The round is asked again once, out of sight, with the nudge "you were repeating yourself … decide and answer" and Ollama's `repeat_penalty` 1.2 (sent only for this retry); an answer that chanted keeps its first round. A second loop ends the reply as an error that says so (or as the kept text), never as a wall of repeats. **Calls:** `ChatSession.loopCalls` counts the calls of the turn that repeat an earlier one (same tool, same arguments, nothing changed in between; failed calls count too, `wait` and `current_time` do not): at `loopCalls` repeats (default 3) the model gets an out-of-sight "step back, use different arguments or answer" message, at twice as many the tools are taken away for the rest of the question (`Generation.toolsHalted`) so it must answer. A change or command that worked, and every new question, starts the count again. Settings → Opinions → *Loop guard: repeated text / repeated calls* (0 = never); each intervention is an event (`loop`: `text`, `calls`, `halt`) on Usage → Orchestration. The tokens of a stopped round are not counted (Ollama never sends its totals).
- **A limited search backend is worked around:** if the chosen backend refuses (DuckDuckGo answers a human check with HTTP 202 from some connections), the other backends that are set up (Brave key, SearXNG address) are tried automatically; DuckDuckGo is left alone for 10 minutes after it blocks; with nothing else set up the model is told not to retry and the user how to fix it (Settings → Tools → Search backend / Search API key).
- **Thinking pane (`thinkingPane`, Settings → Console, `/thinking`):** a split window beside the conversation (bottom, top, left or right: `thinkingPanePlacement`) that follows what a reasoning model thinks while it streams (`Generation.liveThinking`, updated every 100 ms at most; at most 20,000 characters per round) and, when idle, shows the last thoughts of the last answer. `Ctrl+T` (`Key.Thinking`, `resizeThinkingPane`) steps the size through 15/25/35/50/75/85 % and saves it, then turns the pane off and resets the size to 15 (the next press switches it on); `thinkingPanePercent` (10-90, default 30) is a percent of the main axis (of the conversation's height for bottom and top, of the content width for left and right; `thinkingPaneLayout`), it shows the END of the stream, word-wrapped (`wrapWords`); title `Thinking · model · live · 4.7k characters`. A strip takes its rows from the conversation (counted in `outputRows`, which keeps at least 5), a column takes columns (the conversation keeps at least 40) and needs a window of 80 columns and 16 rows, else the pane goes to the bottom; a strip is left out when the terminal is under 26 rows; the pane stays while a question or an approval is open (the dialog's rows come out of the conversation, so a strip may be left out when little is left). It needs a model that streams thoughts (Ollama's `thinking` field; the model list in Settings → Ollama marks the capability); for any other it says so. The thoughts are also kept with the answer as before (*Thinking in Chat*). Not the `/compare` split view, which is columns of answers.
- **Nothing is cut silently:** tool results of earlier questions are sent whole (`oldToolOutput = "whole"`, the default; `shorten` cuts them to 1,200 characters with an explicit marker). A cut a tool makes itself (`read_file` after 20,000 characters, a long list, shell output, a web page) ends in a marker line, which the chat shows in orange under the result (`✂ …`, `ToolCuts.marker`, `Chat.toolResultLines`).
- **`todo` (the model's task list):** for a job of three or more steps the model writes its plan with `todo` (one `[ ]` / `[~]` / `[x]` item per line, the whole list each call) and calls it again to tick items off. The chat shows the list under the call (`☐ ▸ ☑`), the status bar a `☑ done/total` pill, and the result tells the model what is next (and "give the final answer" when all are done). It is not a gate: a skill's `requires:` still decides when a run may end. See `Todos.kt`.
- **`chat_stats` and the Oracul:** the tool also reports how the Oracul is set (`Oracul.setupLine`), the second opinions, comparisons, plans and takeovers in the chat with their models (read from the blocks), and, from the Usage records (`ChatStats.spendLines`): **token spend per model** since Arcana started (read + generated = total, requests, what each model was used for such as `Chat ×149, Compact ×4`, estimated cost, busiest first) and a **total**, then how many times the Oracul, the judge and the planner were **called in all the history** (the usage file keeps it across restarts, with how many were this session).
- **Another server (`oraculUrl`, Settings → Helpers → *Oracul server*):** the Oracul and the judge (also a skill's `reviewer:` and `/takeover`) ask that Ollama server instead of the main one (`ChatSession.clientFor` → `Oracul.serverConfig`); the pickers list what is installed there. Blank = the main server. Only Ollama. The question, the answer and what its tools read are sent to that server, so the setting's help says so.
- **Artifacts (`✦ 3 changed` pill, `/artifacts`):** the files and notes the model's tools wrote or changed in this chat (`Artifacts.of`: `create_note`, `write_file`, `edit_file`, `append_to_note`, `set_properties`, `add_tags`, `move_path` (the new path), `delete_path`; a read, a command, a denied or failed call leaves nothing; `remember` is the memory line, not an artifact). The pill counts distinct paths; `/artifacts` (or `Esc` then `f`, or Ctrl+P → *Files and notes changed in this chat*) lists them newest first with what happened, and `1`-`9` opens a note in the Library. It lives in memory in `ChatSession.artifacts` for this chat: `/new` and opening another chat clear it, and it is not saved.
- **Model state (the `● loaded 7.7 GB 100% GPU` / `○ not loaded` indicator in the Chat status bar, with `· 2 models 17.3 GB` (everything Ollama holds) when more than one model is loaded (this indicator now lives in the bottom bar on every screen), and the *Waiting for <model>…* line):** while a request has produced no word yet, `ModelStatus.describe` says why, from `/api/ps` and the machine: *loading <model> into memory* (and which other models are loaded and may be unloaded first), *loaded, reading about 12k tokens of conversation* (an estimate, `ChatSession.promptEstimate`: Ollama does not report the progress of reading a prompt, so no time is promised), *35% of it runs on the CPU, so slowly*, *memory is tight (swap 88% full)* (`SystemMemory.swapPercent`, macOS). The first clause is an orange pill in the Chat status bar (`AppContext.modelWhy`; the whole sentence stays in the reply line) and is added to the helper-model line (`Ψ qwen3.5:9b is checking the answer… 137s · …`). When nothing is waited for, the bar shows whether the chat model is loaded and how much of it is on the GPU (`AppContext.loaded`, refreshed after replies and helper work).
- **Hardware warnings (in the footer bar, next to the model badge, on every screen; `hardwareWarnings`): `⚠ 35% on CPU: slow, lower the context` (red), `⚠ ctx 256k > model 128k` and `⚠ ctx 4k is small` (orange); the explanations are in the *Context window* hint in Settings.** The first is about the CPU: Ollama says in `/api/ps` how much of a loaded model did not fit in graphics memory (`size` against `size_vram`); a model with 10 % or more on the CPU is several times slower, and a long prompt can run into the timeout (*Cannot reach Ollama: request timed out*). `OllamaProtocol.parseOffloads`, `OllamaClient.offloads`, `AppContext.offloads`, refreshed after a reply and when a helper model finishes. The usual cause is a context window too large for the machine: the cache for the window is allocated up front.
- **Switches (Settings → Helpers → *Helper models* and *Skill roles*; `/helpers`, `/roles`):** *Helper models* turns every model but the chat model on or off at once (Oracul, judge, flow, specialists, router; their settings are kept); *Skill roles* turns the worker / planner / reviewer of skill runs on or off. They are independent, so you can test one model alone, one model with skill roles, and so on. See [oracul.md](oracul.md#the-two-switches).
- **Specialists as tools (Settings → Flow → *Specialists as tools*):** the chat model may call the analyst, the planner or the reviewer itself with the `consult` tool (a brief in, the specialist's text out; at most 3 per message), instead of the fixed *Flow* sequence. See [oracul.md](oracul.md#specialists-as-tools-consult).
- **Router (Settings → Helpers → *Route: images to* / *Route: code to*):** a message with an image goes to the vision model, one with a code block or a source file name to the code model, by simple rules; blank = the chat model. A skill's or flow's own worker wins, and a model that is not installed or cannot read images / use tools is skipped with a note. See [oracul.md](oracul.md#router).
- **`/goal <condition>`:** sets a goal that stays the main idea of the chat (it is in the system prompt of every request and shown as `◎ goal` in the status bar) and starts the work; after each reply a checker says met or not met and, while not met, the worker is sent on by itself (up to *Goal turns*, default 5). `/goal` shows it, `/goal clear` drops it. See [oracul.md](oracul.md#judge-verdict-and-goals).
- **After an agreeing verdict a dialog asks what to do** (revise now, leave it, revise automatically from now on, or type a note of your own for the revision) instead of leaving you to type `/revise` (*When the judge agrees*: Ask / Revise automatically / Advice only). **Finish open todos:** a model that ends its turn with open steps on its own todo list is sent back once.
- **Judge verdict:** after an automatic second opinion the judge model (when set) says AGREE / PARTLY / DISAGREE (*Judge verdict on opinions*, on by default).
- **`/flow [name]`:** switches the flow on or off (`/flow` toggles, `/flow careful` / `/flow off` set it; `slashState` shows `OFF` or the name). While a flow works, the reply line names the stage (`Ψ <model> is analysing the request…` / `planning…` / `reviewing the answer…` / `checking the answer…`, `ChatSession.consultingStage`) and the status bars add `⇉ careful` (`Oracul.statusText`). Esc (after the question) cancels the running stage and the rest of the flow.
- **Flow (Settings → Flow → *Flow*, `flow` / `flowAnalyst`):** *Careful* sends every message through analyst → planner → worker → reviewer → controller, each its own model (an unset stage takes the Oracul model; the worker is the chat model). The controller says done or redo; on redo the worker is sent back with what to fix, up to *Flow redos* times (default 2). Messages under 60 characters go straight to the worker. *Flow check command* adds an objective check: a shell command (`./gradlew test`) run after each answer; a failing exit code redoes the work with the output, a passing one is told to the controller (needs shell + auto-run). Details in [oracul.md](oracul.md#flows-orchestration).
- **Role table (Settings → Skills → *Skill planner / worker / reviewer*, `rolePlanner` / `roleWorker` / `roleReviewer`):** defaults for skill runs; a role a skill names in its own properties wins (`SkillRoles.withDefaults`). Outside a skill run nothing changes, unless *Roles apply to* is *Every message* (`rolesScope` = `all`): then the table runs as a pipeline for every message (a plan first for messages of 60 characters or more, the worker answers, the reviewer checks). The planner and reviewer pickers list the models of the Oracul server, the worker picker those of the main one.
- **Planner:** at the start of a skill run (chip), `ChatSession.plan` asks the planner (no tools) for a short plan from the question and the skill text and adds it as a `Ψ Plan · <model>` block (`Oracul.MARK_PLAN`; an Oracul block for every purpose but `/revise`: `isOpinion` yes, `isReview` no), which the worker then sees. A planner that is missing or fails only leaves a message.
- **Roles per skill:** `worker:` / `reviewer:` (and `planner:`) in a skill's properties (see [skills.md](skills.md)): `ChatSession.applyRoles` checks them against `/api/tags` (and the `tools` capability) when a skill chip or `use_skill` starts the run; the worker answers that message in place of the chat model (usage is recorded under it), the reviewer's second opinion is added when the answer is done even if the automatic trigger is off. Cleared by the next message, a new or opened chat.
- **`/takeover` (escalation):** when the worker failed the turn (an error or an empty reply after its retry, `GenState.Failed`) the Chat shows a toast "Type /takeover to let <model> finish it" (only when an Oracul model is set and the automatic trigger is not `off`; never automatic, you decide). `/takeover` (also in the palette, enabled while the turn is failed) calls `ChatSession.takeOver`: the Oracul model continues from the same history (`Compaction.forModel`, memory and attached notes, its own model's prompt), with its tools when it has them (`oraculAgent`, every change still asks). Its answer is added as an ordinary assistant reply headed `Ψ <model> took over this turn` (`Oracul.takeoverHeading`). Refused when there is no Oracul model or when the last message is already an answer. Tokens are recorded as `Oracul`.
- **The hint:** while an opinion is open the block ends with "› /revise: the main model corrects its answer with this · or just carry on" (`opinionLines(applyHint)`); once the worker or you have said something it is gone.
- **Where it shows:** the bottom bar has a badge next to the model pill, `Ψ <model> ⚖ <judge> · auto` (the `⚖ <judge>` part only when the judge is another model than the Oracul; `· auto` = `problems`, `· always` or `· manual`) (orange `Ψ <model>…` while it is being asked); nothing when no Oracul model is set (`Shell.oraculBadge`). The Chat status bar shows the same text when idle (`Oracul.statusText`, one function for both bars, priority 8 so a crowded bar drops other pills first) and an orange `Ψ <model>…` while the Oracul works, `⚖ <judge>…` while the judge does.
- **In the chat:** a block `Ψ Second opinion · <model>` (or `Ψ Comparison · worker vs oracul, judged by judge` with both answers and the verdict). It is stored as a *user* message starting with `Oracul.MARK`, so the worker sees it in the history and can act on it when you go on; compaction and `chat_stats` do not count it as one of your turns; saved transcripts name it. Tokens are recorded in Usage under the model that spent them, as feature `Oracul` (opinions, its answers, takeovers, stepping in), `Judge` or `Planner`, so each can be counted and shows in Usage → By feature. The status bar shows `Ψ <model>…` first while it works, and the main model after it as `waiting`.

- **On/off is the only lever** on Qwen3/3.5 and Gemma 4; levels (`low`/`medium`/`high`) are ignored, so Arcana asks `/api/show` → `thinking.values` and sends a level only to a model that lists it (gpt-oss style). Locally gemma4:26b, qwen3.5:9b and qwen3:14b all say `{"values": [false, true], "default": true}`.
- Thinking tokens count against `num_predict` and the context window, so thinking fills the window faster (it matters for compacting).
- The reasoning arrives in `message.thinking`, not as `<think>` tags in `content`; some Qwen3/DeepSeek-R1 GGUFs and other servers still write the tags. Qwen3 (not 3.5) also takes `/think` and `/no_think` in the prompt; Gemma 4 has no such switch (its real control token is `<|think|>` in the system prompt, set by the chat template, not a `<!think>` token).
- `/api/show` → `capabilities` (`thinking`, `vision`, `tools`, `audio`) feeds the abilities in the bottom bar. `MoE` appears only when `model_info["<arch>.expert_count"]` is there; gemma4 on the MLX runner does not report it (it is an MoE, about 4B active of 26B), and a guess from the name (`-a3b`) was left out.
- **Reasoning effort per message (built):** `Ctrl+G` or `/effort` (the old name `/think` still works, so the pane command `/thinking` is not mistaken for it; `/effort xhigh` sets a level directly, `/effort auto` the model default, `/effort settings` back to the Settings value) opens a list of **the choices the current model offers** (read from `/api/show` → `thinking.values`, never hardcoded: `off · on` for Qwen3.5 / Gemma, `low · medium · high` for gpt-oss, `off · low · medium · xhigh` for qwen3.8; `false`/`true` are shown as off/on). `Enter` uses the pick for the **next message only** (kept on the message as `ChatMessage.think`, shown as `You · ✦ think xhigh`; every tool round of that message uses it); `d` makes it the Settings value. The control sits inside the message field, at the right end of its first row, `Ctrl+G ✦ think xhigh` (no row of its own; the typed text wraps in the room left; a narrow window drops it, the status bar still shows the level): its colour says the level at a glance and does not move (`thinkColor`: off blue, the model's lowest level green, middle levels orange, highest red; `on` orange; `auto` takes the colour of the model's real default); the same colours mark the choices in the `Ctrl+G` list and the status bar. Settings → Ollama → Thinking & effort lists the same model-driven choices (`ThinkLevels`). Each choice is explained in plain words (`thinkEffect`: off = fastest, on = reasons first, the model's lowest / middle / highest level = light / balanced / deepest, more thinking tokens use more of the context window) in the picker's hint and under the Settings row. `auto` always shows the model's real default from `thinking.default` (`auto (medium)`, `auto (on)`), blank only when Ollama does not say. A level the model does not list is not sent.
- **The model knows its levels:** the system prompt carries a static `REASONING EFFORT` note (`Prompts.effortNote`, only for a model that can think, only for the chat model): the levels THIS model offers, its default, and how the user picks one (`Ctrl+G`, `/effort`, Settings), so it can answer "how do I make you think harder?" and suggest a level for a task. It does not name the level in use (that changes with every pick and would make the model read the whole chat again). The same text is in the vault's `Arcana LLM Reference`.
- **Not built yet:** parsing inline `<think>…</think>` from `content` into the thinking pane.

## Compacting a chat

`/compact` (or Ctrl+P → "Compact the chat") asks the model (the chat model) to summarize everything before the latest turns that fit in *Keep after compacting* (`compactKeepPercent`, default 30 % of the context window, at least the last turn; 0 = the last 2 turns) (`Compaction.cutPoint(messages, keepTokens)`, at least 4 older messages) and inserts the summary into the chat at that point (`ChatSession.compact`). Nothing is removed: the messages above stay on screen and in saved notes, under a dim divider "◌ compacted: the model sees this summary instead of the messages above"; only `Compaction.forModel` (from the latest summary on) decides what the model is sent, and a later compaction chains onto the earlier summary. The summary is a `user` message starting with `Compaction.MARK`. **Auto-compact** (`autoCompactPercent`, default 80, Settings → Console → *Auto-compact*) does the same inside `ChatSession.ask` before a message when the last request filled that share of the window (`autoCompactDue`); a failure is ignored and the message goes out as it is. The summary request is recorded in Usage as feature `Compact`; the status bar shows `◌ compacting…` meanwhile.
